# 교육주제에서 웹 발표자료까지

사용자가 주제 한 줄을 입력하면 인터뷰를 시작한다. 답을 들으며 교육 설계판을 갱신하고, 사용자와 시나리오를 확정한 다음 실제로 열리는 HTML 파일까지 완성한다. 이 스킬은 에이전트의 작업 절차다. HTML 생성 스크립트 자체가 AI를 호출하거나 주제를 이해하는 것은 아니다. 시나리오와 문장은 대화에서 함께 설계하고, 확정된 콘텐츠를 스크립트로 조립한다.

## 시작: 주제에서 인터뷰로

1. 현재 요청과 대화에서 주제, 대상, 숙련도, 시간, 교육 후 할 수 있어야 하는 행동, 현장의 문제, 도구/환경, 실제 사례·자료, 원하는 분위기를 추출한다.
2. 주제가 없으면 주제부터 묻는다. 주제만 있으면 완성안을 만들지 말고 인터뷰의 첫 질문을 한다.
3. 한 번에 핵심 질문 하나만 한다. 서로 붙어 있어야 답할 수 있는 항목만 두 개까지 묶는다. 이미 답한 내용은 다시 묻지 않는다.
4. 질문에는 왜 필요한지 한 문장으로 알려주고, 사용자가 막히지 않도록 2~3개의 구체적인 답 예시 또는 추천안을 붙인다. 사용자가 `추천해줘`, `모르겠어`, `알아서`라고 하면 맥락에 맞는 안을 제안하고 가정으로 표시한다.
5. 답을 받을 때마다 `지금까지 정해진 것`을 2~4줄로 갱신하고, 새 답이 시간표나 실습에 미치는 영향을 짧게 보여준 뒤 다음 질문으로 간다. 인터뷰 도중 장문의 완성 시나리오를 쏟아내지 않는다.
6. 최소한 **대상**, **교육 후 행동/결과물**, **시간**, **현장 환경과 실습 가능 여부**를 알아야 1차 시나리오로 넘어간다. 실제 사례·현재 어려움·말투/분위기는 품질을 높이는 질문으로 다루되, 사용자가 충분하다고 하면 추천안으로 채운다.
7. 교육 시간·기기 유무에 맞춰 실행 가능한 실습을 제안한다. PC가 없으면 관찰·종이 활동·짝 토론으로 바꾼다.

인터뷰는 심문처럼 길어지면 안 된다. 보통 4~6개의 적응형 질문이면 충분하다. 사용자가 처음부터 필요한 조건을 다 주면 요약한 설계판을 제시하고, 가장 큰 선택 하나만 확인한다. 사용자가 `바로 초안`, `나머지는 추천`이라고 하면 가정을 명시하고 1차 시나리오로 진행한다.

권장 질문 순서이며, 대화에 따라 건너뛴다.

1. 누가 듣는가: 직무·숙련도·인원, 이 주제를 지금 배우려는 이유
2. 끝나면 무엇을 해내야 하는가: 눈에 보이는 결과물 또는 행동
3. 시간과 현장: 총시간, PC/인터넷/계정, 개인 실습·시연·토론 가능 여부
4. 현실 연결: 자주 겪는 실패, 실제 사례나 자료, 꼭 다룰 장면
5. 전달 방식: 강연/워크숍 비율, 분위기, 피해야 할 표현

첫 답변 예시:

```text
좋아요. 먼저 이 교육을 듣는 사람을 정해야 난이도와 사례가 맞아집니다.
누가 듣나요? 예: AI를 처음 쓰는 공무원 / 신규 직원 / 실무 경험이 있는 개발자
```

출력 위치는 사용자가 지정한 곳을 우선한다. 없으면 저장소의 `workshops/<짧은-주제-slug>/`를 쓴다. 인터뷰 중에는 대화의 설계판을 기준으로 삼고, 1차 시나리오 단계에서 `brief.md`를 만든다. 동일 이름 파일이 있으면 읽고, 수정 요청이 아닌 신규 제작은 새 폴더명으로 구분한다. 기존 앱과 기존 발표자료를 바꾸지 않는다.

## 합의 지점

1. 필수 답이 모이면 `대상 / 문제 / 교육 후 행동 / 시간·환경 / 추천한 교육 방식 / 남은 가정`을 한 화면 분량으로 정리한다.
2. 사용자에게 잘못 이해한 점이나 바꿀 점을 묻는다. 사용자가 확인하거나 `초안 보여줘`라고 하면 `brief.md`와 `scenario.md` 1차안을 만든다.
3. 1차안은 시간표와 핵심 장면을 먼저 보여주고, 가장 영향이 큰 선택을 구체적으로 묻는다. 예: “Git 명령 설명 10분을 줄이고 에이전트 실습을 10분 늘릴까요?”
4. 답을 반영해 파일과 요약을 함께 갱신한다. 사용자가 `좋아`, `확정`, `발표자료 만들어줘`처럼 시나리오를 승인할 때까지 HTML 제작으로 넘어가지 않는다.
5. 승인 후에는 반복해서 확인받지 않고 슬라이드 제작·검증을 끝낸다. 사용자가 `기획만`이면 승인된 scenario까지, `시나리오 먼저`이면 1차안 검토 단계에서 멈춘다.

출력 위치는 사용자가 지정한 곳을 우선한다. 없으면 저장소의 `workshops/<짧은-주제-slug>/`를 쓴다. 동일 이름 파일이 있으면 읽고, 수정 요청이 아닌 신규 제작은 새 폴더명으로 구분한다. 기존 앱과 기존 발표자료를 바꾸지 않는다.

## 1. 교육 설계판과 brief

`references/content-contract.md`를 읽고 다음을 `brief.md`에 쓴다.

- 주제·대상·시간·선행지식·도구·환경
- 관찰 가능한 학습목표 2~3개: “이해한다”만 쓰지 말고 “구분한다/작성한다/실행한다/검증한다”로 표현
- 학습자가 가지고 돌아갈 결과물 1개
- 사용자 답변으로 정한 조건과 에이전트가 추천해 채운 가정
- 범위 밖 내용과 자료 확인 상태

법령·통계·제품 기능·가격·최신 버전 등 확인이 필요한 내용은 공식 자료를 조회한다. 로컬 프로젝트가 주제라면 먼저 실제 파일을 확인한다. 확인하지 않은 숫자·인용·성공 사례는 만들지 않는다. 교육용 가상 사례는 그렇게 표시한다. 웹을 사용할 수 없으면 변동 가능한 주장을 제외하거나 확인 필요로 남기고 한계를 보고한다.

## 2. 함께 다듬는 시나리오

합의한 설계판을 바탕으로 `scenario.md` 1차안을 만들고 대화에서 수정한다.

- 강의 중심 질문 1개와 교육 후 변화 1문장
- 시작 훅 → 목표·아젠다 → 개념·시범·활동 → 적용·회고 → 자료·Q&A → 다음 행동
- 구간별 시간표. 설명·전환·실습·질문 시간을 포함한 합계가 전체 시간과 같아야 한다.
- 강사의 실제 멘트, 청중에게 던질 질문, 장면 전환 문장
- 실습별 시작 상황, 입력 자료, 학습자 행동, 복사 가능한 프롬프트(해당 시), 결과물, 성공 기준, 막혔을 때 대안

설명 뒤 바로 해볼 작은 행동을 배치한다. 실습 수를 고정하지 않는다. 15분 강연에 긴 실습을 억지로 넣지 말고, 60~90분 워크숍에는 수행과 검증 시간을 충분히 확보한다. 에이전트 활용 교육은 학습자가 **상황 설명 → 프롬프트 설계 → 에이전트 실행 → 결과 검증**을 경험하게 한다. 사용자의 수정 의견은 해당 장면뿐 아니라 목표·시간표·전환에도 반영하고 합계를 다시 맞춘다.

## 3. 슬라이드와 디자인 결정

`slides`가 있으면 SKILL.md와 교육 전략·레이아웃 관련 참조를 읽고 적용한다. `design-system/scripts/search-slides.py`가 실제로 있으면 워크숍 전략/레이아웃을 조회할 수 있다. 경로를 `.claude`로 고정하지 말고 설치 위치를 확인한다. Windows Python은 `PYTHONUTF8=1`을 쓴다. 검색 추천은 참고 자료이며 내용·레이아웃 검증 통과의 증거로 쓰지 않는다.

추가 스킬이 없어도 이 패키지만으로 계속한다. `find-skills` 검색·외부 스킬 설치를 매번 필수로 만들지 않는다. 도입할 때만 검색하고 설치는 사용자의 요청 범위에서 한다.

한 장의 역할은 한 문장으로 정한다. `deck.json`에 제목, 핵심 문장, 레이아웃, 시간, 노트, 근거를 작성한다. 시간과 장수는 이 파일을 기준으로 삼고 시나리오와 대조한다. 본문보다 노트가 상세해야 한다. 긴 목록/프롬프트는 장을 나누거나 노트로 옮긴다.

기본 시각 언어는 큰 한글 제목, 높은 대비, 한 장 한 메시지, 핵심어 강조, 개념과 실습 사이의 화면 변화다. 사용자가 “슈카월드 스타일”을 원하면 질문형 훅·일상 비유·큰 키워드·장면 전환의 리듬으로 해석한다. 로고·인물 사진·확인되지 않은 인용을 넣지 않는다. 앱의 대시보드 디자인 규격과 발표 매체의 규격을 구분한다.

기본 템플릿은 hero/cards/split/steps/prompt 5가지다. 실제 정량 데이터가 없으면 장식용 통계 차트를 만들지 않는다. 다른 스타일이나 실제 차트가 필요하면 근거와 요청 범위에 맞춰 템플릿을 확장하고 다시 검증한다. 오프라인 산출물에는 외부 CDN 의존성을 남기지 않는다.

## 4. HTML 제작

`references/content-contract.md` 형식에 맞는 `deck.json`을 만들고 아래 명령을 **에이전트가 실행**한다. 경로는 실제 패키지 위치와 출력 폴더에 맞춘다.

```text
node workflows/education-web-deck/scripts/render-deck.mjs workshops/<slug>/deck.json --check
node workflows/education-web-deck/scripts/render-deck.mjs workshops/<slug>/deck.json workshops/<slug>/index.html
```

수정 요청으로 기존 HTML을 다시 만들 때만 대상 확인 후 `--force`를 쓴다. 생성된 HTML 직접 편집은 다음 생성 시 사라지므로 콘텐츠는 JSON, 공통 디자인/동작은 템플릿을 수정한다.

결과물은 CSS/JS가 포함된 단일 HTML이다. 열람에는 Node나 앱 서버가 필요하지 않다. 생성 시에는 Node 20 이상이 필요하다. JSON 렌더링만으로 사실성·교육 효과·화면 품질이 검증된 것은 아니다.

## 5. 검증과 수정

`references/quality-checklist.md`를 읽고 실행한 검증과 결과를 `qa.md`에 기록한다.

1. 목표와 활동·성공 기준이 연결되는지, 시간 합계가 맞는지, 아젠다·자료·Q&A·노트가 빠지지 않았는지 점검한다.
2. `--check`로 콘텐츠 계약을 검사한다. 정적 구조 통과와 사실 검증을 구분한다.
3. 브라우저로 모든 장을 확인한다. 긴 프롬프트, 한글 줄바꿈, 1366×768/1920×1080 및 좁은 화면, 조작·복사·해시·인쇄를 확인한다. 브라우저 사용이 불가능하면 미실행 항목을 명시하고 통과로 표시하지 않는다.
4. 네트워크 없이 기본 발표 기능이 작동하는지 확인한다. 외부 자료 링크를 여는 것과 HTML 열람을 구분한다.
5. 저장소에 빌드 지침이 있으면 따른다. 이 저장소에서 코드 수정 후 `npm run build`를 실행한다. 해당 빌드가 HTML 화면 검증이나 별도 lint 실행을 대신한다고 말하지 않는다.
6. 오류가 있으면 고치고 관련 항목을 다시 검사한다. 선택적으로 다른 에이전트가 초보 학습자 시점으로 읽게 한다.

발표자 노트는 같은 화면에 뜬다. 화면을 공유하면 청중도 볼 수 있음을 전달한다.

## 6. 전달과 재사용

최종 응답에는 파일 링크, 대상·시간·장수, 열기/조작 방법, 검증 결과와 미확인 항목만 간결히 전달한다. 기본 산출물:

```text
workshops/<slug>/
  brief.md       # 입력과 가정, 목표
  scenario.md    # 시간표, 강의·활동 시나리오
  deck.json      # 슬라이드 콘텐츠 원본
  index.html     # 발표 때 여는 단일 파일
  qa.md          # 실제 검증 증거와 남은 항목
```

사용자의 배포 요청이 있으면 저장소·대상을 확인해 그 범위에서 커밋/푸시/호스팅한다. 제작 요청만으로 배포 완료나 URL 접속 가능을 주장하지 않는다. 두 번째 PC에서는 이 워크플로우 폴더와 원본을 가져오고 같은 실행 문장을 사용한다. 글로벌 스킬 설치 여부에 의존하지 않도록 파일 경로로도 실행할 수 있게 안내한다.
